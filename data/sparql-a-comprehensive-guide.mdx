In the [previous article](/blog/category/data/everything-you-need-to-know-about-rdf), we explored everything you need to know about [RDF](https://www.w3.org/TR/rdf11-primer), its structure, and its purpose in representing data in a standardized, graph-like format. Now, let’s dive into how to query RDF data, enabling you to extract meaningful insights from RDF graphs efficiently. This guide will cover the basics, common querying tools, advanced querying techniques, and best practices, ensuring you’re well-equipped to handle RDF data.

RDF organizes data into triples in the form of **subject-predicate-object**, which collectively form a directed graph. Each triple represents a relationship, making RDF an ideal format for data that contains intricate relationships, hierarchies, and dependencies.

Querying RDF data allows you to retrieve meaningful subsets of data, answer complex questions, or explore relationships between resources. The standard approach for querying RDF is [SPARQL](https://www.w3.org/TR/sparql11-query/), a language specifically designed to navigate and manipulate RDF graphs.

[SPARQL](https://www.w3.org/TR/sparql11-query/), standardized by W3C, functions as both a query and update language. Its graph-based nature aligns perfectly with the RDF structure, enabling sophisticated querying mechanisms beyond the capabilities of traditional relational query languages like SQL. If this is the first time you look at SPARQL, but you are familiar with [SQL](https://en.wikipedia.org/wiki/SQL), you will see some similarities because it shares several keywords such as `SELECT`, `WHERE`, etc. It also has new keywords that you have never seen if you come from a SQL world such as `OPTIONAL`, `FILTER` and much more.



## SPARQL: The Standard Query Language for RDF

[SPARQL](https://www.w3.org/TR/sparql11-query/) is designed to work seamlessly with RDF data. It supports a wide range of features, including data retrieval, filtering, aggregation, and updates to [RDF](https://www.w3.org/TR/rdf11-primer) graphs. [SPARQL](https://www.w3.org/TR/sparql11-query/) can be used for:
- **Retrieving Data**: Extract specific nodes, edges, or patterns from the graph.
- **Graph Navigation**: Traverse relationships in the [RDF](https://www.w3.org/TR/rdf11-primer) structure.
- **Aggregation**: Summarize data with counts, averages, and other operations.
- **Data Manipulation**: Insert, delete, or modify triples in RDF datasets (via [SPARQL](https://www.w3.org/TR/sparql11-query/) Update).

## SPARQL Query Structure

A [SPARQL](https://www.w3.org/TR/sparql11-query/) query generally consists of the following parts:
1. **PREFIX**: Shortens long URIs for readability and usability.
2. **SELECT/ASK/CONSTRUCT/DESCRIBE**: Defines the type of result (e.g., tabular, graph, or boolean).
3. **WHERE**: Specifies the graph patterns to match.
4. **ORDER BY/LIMIT/OFFSET**: Controls result sorting and pagination.

## Basic SPARQL Queries

Assume we have the following RDF triples in our database

```turtle
@prefix foaf: <http://xmlns.com/foaf/0.1/> .
@prefix aa: <http://example.org/Personal#> .

<http://example.org/blog1> foaf:name "Ahmad's Blog" .
<http://example.org/blog1> aa:owner <http://example.org/Assaf> .
<http://example.org/Assaf> foaf:name "Ahmad Assaf" .
<http://example.org/Assaf> foaf:based_near <http://example.org/London> .

<http://example.org/blog2> foaf:name "Overfit.in" .
<http://example.org/blog2> aa:owner <http://example.org/Ahmad> .
<http://example.org/Ahmad> foaf:name "Ahmad" .
<http://example.org/Ahmad> foaf:based_near <http://example.org/Manchester> .
```

### Finding Blog Names and Their Owners

Find all the names in the database, then narrow the results down to just the blog owners.

::: code-group labels=[Finding All Names, Finding Blog Owners' Names]

```sparql
SELECT ?name
WHERE {
  ?x foaf:name ?name
}
```

```sparql
SELECT ?ownerName
WHERE {
  ?blog aa:owner ?owner .
  ?owner foaf:name ?ownerName .
}
```

:::

Let’s break down the first query, which gets every name in the database. The query starts with the keyword `SELECT` and afterwards are the variable names that we would like to project, which in this case is `?name`. <Highlight>Note that all variable names have a question mark in the beginning</Highlight>.  Afterwards, we find the `WHERE` keyword which is followed by a triple between curly braces. This triple is the most interesting part. The triple in the query must also consist of a **subject**, **predicate** and an **object** but in this case, either one can be a variable. In this case, the subject and the object are variables while the predicate is a constant value. This triple in the query is evaluated against all the RDF triples in your database. Constant values in the query triples are matched with constant values of the RDF triples in your database. For example, in our query triple, the only constant value is in the predicate which is `foaf:name`. Out of our eight RDF triples, four of them have `foaf:name` as a constant in the predicate, therefore these four RDF triples match our query triple. Note that nothing in the query restricts `?x` to blogs: anything with a `foaf:name`, blogs and owners alike, matches.

```shell
?x = http://example.org/blog1, ?name = "Ahmad's Blog"
?x = http://example.org/Assaf, ?name = "Ahmad Assaf"
?x = http://example.org/blog2, ?name = "Overfit.in"
?x = http://example.org/Ahmad, ?name = "Ahmad"
```

Because our query is only selecting the values assigned to the variable `?name`, the final answer is **Ahmad's Blog**, **Ahmad Assaf**, **Overfit.in** and **Ahmad**.

### Chaining Queries: Getting Blog Owners' Names

The second query shows how to narrow that down by chaining two triples. In the first triple, the predicate has a constant value of `aa:owner` and the object is a variable. This triple will match the RDF triples that have the predicate `aa:owner` and will assign the value of the object to the variable `?owner`. The second triple will then match the RDF triples that have the predicate `foaf:name` for those owners and assign the value of the object to the variable `?ownerName`. 

The result will be two triples with the values `Ahmad Assaf` and `Ahmad` because these are the only owners of the blogs in our RDF triples.

### Filtering by Location

Find the names of blog owners based near London.

```sparql
SELECT ?ownerName
WHERE {
  ?blog aa:owner ?owner .
  ?owner foaf:name ?ownerName .
  ?owner foaf:based_near <http://example.org/London> .
}
```

In this query we have three triples. The first two are the same as in our previous example and we already know the solution to them. Now let's look at the third query triple. In this case, the predicate has a constant value of `foaf:based_near` and the object has a constant value of `<http://example.org/London>`, which can only match one of our RDF triples.

The result will be one row with the value `Ahmad Assaf` because he is the only owner based near London.

### Query for Relationships

If you have a triple pattern in a query where the predicate is a variable, then you can explore the database to find relationships. For example, the query

```sparql
SELECT ?p
WHERE {
  <http://example.org/blog1> ?p <http://example.org/Assaf> .
}
```

The result is a single binding that reveals the relationship between **blog1** and **Assaf**: the value `aa:owner`. Magic ✨

## Transform Data with CONSTRUCT

Through the `CONSTRUCT` operator, which is an alternative to `SELECT`, [SPARQL](https://www.w3.org/TR/sparql11-query/) allows you to transform data. The result is an RDF graph, instead of a table of results. Imagine you have RDF data that has been automatically generated and you would like to transform it to use well-known vocabularies. For example:

```sparql
PREFIX foaf: <http://xmlns.com/foaf/0.1/> 
PREFIX aa: <http://example.org/Personal#> 

CONSTRUCT {
  ?blog foaf:maker ?owner .
}
WHERE {
  ?blog aa:owner ?owner .
}
```

The result is a new RDF graph where `aa:owner` is replaced by `foaf:maker`.

```turtle
<http://example.org/blog1> foaf:maker <http://example.org/Assaf> .
<http://example.org/blog2> foaf:maker <http://example.org/Ahmad> .
```

## Using `OPTIONAL`

An interesting operator in [SPARQL](https://www.w3.org/TR/sparql11-query/) is `OPTIONAL`. If you are coming from the SQL world, this operator is equivalent to the `LEFT OUTER JOIN`. The question is, why do we need this? Consider the following triples and query:

::: code-group labels=[Data/RDF, Query/SPARQL]

```turtle
:id1 foaf:name "Ahmad Assaf" .
:id1 foaf:based_near :London .
:id2 foaf:name "Ahmad" .
```

```sparql
SELECT ?name ?loc
WHERE {
  ?x foaf:name ?name .
  ?x foaf:based_near ?loc .
}
```

:::


If you are coming from the SQL world, you would expect two results: `{?name = "Ahmad Assaf", ?loc = :London}` and `{?name = "Ahmad", ?loc = null}`. However, there is no triple with subject `:id2` and predicate `foaf:based_near`, therefore there is nothing to join on. Additionally, <Highlight>there are no nulls in RDF</Highlight> so you can't explicitly say that Ahmad has a location which is `null`. Therefore, this solution is not possible. The actual answer is just `{?name = "Ahmad Assaf", ?loc = :London}`. So how do I get the previous results? This is where `OPTIONAL` comes in. The query would have to be:

```sparql
SELECT ?name ?loc
WHERE {
  ?x foaf:name ?name .
  OPTIONAL {?x foaf:based_near ?loc .}
}
```

This query can be read as: “find all the names, and oh by the way, if there is a `foaf:based_near` attached, return that too, otherwise, don't worry about it”. The actual solution would be `{?name = "Ahmad Assaf", ?loc = :London}` and `{?name = "Ahmad"}`.

## Negation Using `FILTER`

The `FILTER` operator is used to filter results based on a condition. For example, if you want to find all the names of blog owners who are not based near London, you can use the following query:

```sparql
SELECT ?name
WHERE {
  ?blog aa:owner ?x .
  ?x foaf:name ?name .
  FILTER NOT EXISTS {
    ?x foaf:based_near <http://example.org/London> .
  }
}
```

This query will return the name of the owner who is not based near London, which is `Ahmad`.

<Callout type="info">

### Negation in SPARQL 1.0

Negation in SPARQL 1.0 is weird. It is based on Negation as Failure and it is implemented using `OPTIONAL`, the `bound` filter, and the `logical-not` operator. The `OPTIONAL` block tries to match the pattern we want to exclude and binds a fresh variable (here `?london`) only when it succeeds; the outer filter then keeps only the solutions where that variable stayed unbound. It is a bit convoluted, but it works and returns the same answer as the query above: `Ahmad`.

```sparql
SELECT ?name
WHERE {
  ?blog aa:owner ?x .
  ?x foaf:name ?name .
  OPTIONAL {
    ?x foaf:based_near ?london .
    FILTER (?london = <http://example.org/London>)
  }
  FILTER (!bound(?london))
}
``` 

</Callout>

## Combining Data with `UNION`

::: code-group labels=[SPARQL Query, Results]

```sparql
PREFIX foaf: <http://xmlns.com/foaf/0.1/>
PREFIX aa: <http://example.org/Personal#>

SELECT ?blogName ?personName
WHERE {
  ?blog foaf:name ?blogName .
  {
    ?blog aa:owner ?person .
  } UNION {
    ?blog foaf:maker ?person .
  }
  ?person foaf:name ?personName .
}
```

```shell
+--------------------+----------------+
| blogName           | personName    |
+--------------------+----------------+
| "Ahmad's Blog"     | "Ahmad Assaf" |
| "Overfit.in"       | "Ahmad"       |
+--------------------+----------------+
```

:::

Against our sample data only the `aa:owner` branch matches, which produces the two rows above; the `foaf:maker` branch would additionally pick up data that uses the FOAF vocabulary directly, such as the graph produced by the `CONSTRUCT` query earlier.

[SPARQL 1.1](https://www.w3.org/TR/sparql11-query/) which was chartered in 2009 came with a lot of the features that were missing from the SPARQL 1.0 specification like aggregates, sub-queries, and a natural negation operator. 

- **Aggregates**: ability to group results and calculate aggregate values (e.g. count, min, max, avg, sum, …).
- **Sub-queries**: allows a query to be embedded within another.
- **Negation**: includes two negation operators: NOT EXISTS and MINUS
- **Property paths**: query arbitrary length paths of a graph via a regular-expression-like syntax
- **Query Federation**: ability to split a single query and send parts of it to different SPARQL endpoints and then combining the results from each one
- **Projected expressions**: ability for query results to contain values derived from constants, function calls, or other expressions in the SELECT list.

A recommended read to learn more about SPARQL 1.1 is the [W3C Recommendation](https://www.w3.org/TR/sparql11-overview/) and [Learning SPARQL Book](https://learningsparql.com/).

## Beyond SELECT

SPARQL is more than a query language for RDF data; a whole ecosystem of extensions has grown around it, expanding what it can do well beyond reading triples. These are the ones I find worth knowing about:

- **[SPARQL Update](https://www.w3.org/TR/sparql11-update/)** introduces write capabilities to the otherwise read-only query language: inserting new triples, deleting existing ones, and creating, clearing, or dropping entire named graphs.
- **[GeoSPARQL](https://www.ogc.org/publications/standard/geosparql/)** is a standardized extension for querying geospatial data within RDF datasets, covering the representation of geometries and spatial relationships and geospatial queries such as distance, intersection, and containment.
- **[RDF-star and SPARQL-star](https://www.w3.org/groups/wg/rdf-star/)** address a long-standing criticism of RDF triplestores compared to Property Graphs: the inability to attach metadata to graph edges. RDF-star lets you make statements about triples themselves, and SPARQL-star lets you query them. What began as a Community Group draft has since moved to the W3C RDF-star Working Group, which is standardizing it as part of RDF 1.2 and SPARQL 1.2.
- **[SPARQL.Anything](https://github.com/SPARQL-Anything/sparql.anything)** is a system for Semantic Web re-engineering that lets you query almost anything (CSV, JSON, HTML, spreadsheets, and more) with SPARQL through the Facade-X meta-model, which represents sources as lists of lists in which blank nodes play a large role. Enrico Daga, one of its key developers, gives a good background on the philosophy in [this talk about streamlining Knowledge Graph construction with a façade](https://www.youtube.com/watch?v=Ak3bykN2dgI).
