When I [put this team together](/blog/category/management/from-employee-six-to-a-unicorn), I wanted experienced engineers who could take a problem and run with it. AI was part of that decision. I expected it to multiply what a small team could do.

A year in, I can see it in what a senior engineer can build in a week. Exploring an approach, producing something we can try, and working through the changes afterwards all take less time than they did. We can get to a working version while the idea is still taking shape.

The [internal dashboard I built](/blog/category/management/becoming-a-cto-building-a-team-when-there-isnt-one-yet) took days. It brought together views of delivery, risk and the people doing the work. I could build a tool around a problem I was trying to solve while still carrying the rest of the job.

## Help with the rest of the job

The job also keeps pulling me into subjects I don't know well. Before making a decision, I need to understand what already exists, where the relevant information is and which question is still unanswered. I use the assistant to bring that context together, and ask for links back to the files or records it used.

That gives me a way into the work. I can open the source behind a claim, ask for an explanation of the part I don't understand, and work through an approach with a diagram. I can also ask it to challenge an assumption while I am still figuring out what I think. I need to inspect the answer closely enough to decide what to do with it.

When the work repeats, I have been writing down the instructions: what to look at, what to do with it, and which decisions need to come back to me. The assistant can follow that procedure and I can inspect the result. The instructions also make the task easier to hand over to someone else. That has been useful when my week moves between engineering, planning and running the company.

## From the prototype to real use

Our product started with a vibe-coded prototype. Once we had design partners and real data, we could see how much there was still to learn. We had to [make room to try things and adjust sooner](/blog/category/management/becoming-a-cto-four-planning-processes-in-a-year).

That is where I find the speed most useful. We can get something in front of us and learn from it. Before we rely on it for customers, I still need an engineer to read the implementation and work through what the demo did not exercise: how it handles failures, protects data and fits the rest of the system.

I don't assume code is poor quality because AI wrote it. It can be useful, well-tested production code. I want to judge the actual change. Does it meet the requirement? Does it belong in this codebase? Can someone else understand it well enough to change it later?

AI can help with that work too: propose tests, explain unfamiliar code, suggest a simpler implementation or work through a failure. The engineer still needs to check the reasoning. If the assistant writes both the implementation and its tests, I want someone to check that they have not simply repeated the same mistaken assumption.

That is what I wanted the team's experience for. An engineer who can frame a problem and recognise when an approach needs changing has more room to work with these tools. I still owe them the outcome and constraints. Faster implementation doesn't help much when a question about what to build is waiting on me.

## Making the help available across the team

Writing down instructions for my own assistant has also made me think about what we should share. As the team grows, I want an agent to be able to find our existing interfaces and patterns, run the tests and build, and work in an environment where it cannot affect production. Each engineer should not have to assemble that context and those access limits again.

There is more to learn here than how quickly a model writes code. I want to understand how much review and rework it takes to finish a change as we try different models.

## 854 pull requests in thirty days

In one thirty-day stretch, our team of roughly ten engineers merged **854 pull requests** across our repositories. AI had become part of how we built, and that was the volume of changes moving through the team.

Those were not 854 features or production releases, and the count does not tell me how much of the code was AI-written. They were changes we needed to understand, test and integrate. I had wanted more capacity to build; now I needed the work around each change to keep up.

An engineer added a check that fails pull requests over four hundred lines, encouraging the coding agent to make smaller, stacked changes. We also built a model-assisted review service to raise findings for the engineer to investigate. Those are two ways we have started using tooling to help with the volume as well as produce it.

Getting those changes into production brought questions of its own. We build for finance, so I need to be able to show how a change got there and who took responsibility for it. We have been [reshaping review and release](/blog/category/management/becoming-a-cto-compliance-at-ai-speed) around independent human approval before production. We are still putting the full process into the tooling.

AI has given me room to build tools I wanted and help with work I was learning as I went. I want to keep that room. The part I cannot hand to the assistant is deciding whether its result does the job: whether the explanation holds up against its sources, the code meets the requirement, or a fix actually addresses the problem it found. That is the work I am putting my name to.

## A few useful reads

- Simon Willison, [Not all AI-assisted programming is vibe coding (but vibe coding rocks)](https://simonwillison.net/2025/Mar/19/vibe-coding/). On the difference between exploring with generated code and taking responsibility for code you understand.
- Birgitta Böckeler, [The role of developer skills in agentic coding](https://martinfowler.com/articles/exploring-gen-ai/13-role-of-developer-skills.html). Examples of the framing, steering and correction involved in working well with an agent.
- GitHub, [Does GitHub Copilot improve code quality?](https://github.blog/news-insights/research/does-github-copilot-improve-code-quality-heres-what-the-data-says/). A vendor-run controlled study finding quality gains on a bounded API task; it does not establish long-term production quality.
- Stripe, [Minions: one-shot, end-to-end coding agents, part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2). How Stripe combines coding agents with repository context, automated checks and human review.
- Uber, [Running a Software Factory Efficiently at Uber Scale](https://www.uber.com/us/en/blog/efficient-software-factory/). A firsthand account of operating and evaluating agents across development, review and maintenance.
- DORA, [Balancing AI tensions: moving from adoption to effective use](https://dora.dev/insights/balancing-ai-tensions/). Research on the benefits engineers report and the verification work that accompanies faster generation.
- Anthropic, [How AI is transforming work at Anthropic](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic). An internal study of coding, code understanding and work engineers previously lacked time to attempt; its productivity estimates are self-reported.
