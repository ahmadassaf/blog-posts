In one thirty-day window, our team of about ten engineers merged 854 pull requests. That number doesn't tell me how much useful product we shipped. It does tell me how much change our review process had to deal with.

We were using AI to build faster, but the review still depended on someone finding the time to understand each change. I wanted that person to open a pull request with some of the preparation already done: which checks had run, where the risk was, what another reviewer had noticed and which decision still needed a human.

So we built a change gate as a GitHub App. It brings together test results, focused model reviews and repository policy. The harder question was how much authority to give its conclusions.

Our first pilot could approve eligible changes. After working through the process with our auditor, we changed the pilot to recommendations for a human reviewer. I wrote about [that change and the wider release process](/blog/category/management/becoming-a-cto-compliance-at-ai-speed) separately. Building the gate also exposed problems with the way we were judging changes: arbitrary size limits, overly influential risk scores and several models confidently repeating the same mistake.

## Start with a decision a reviewer has to make

Consider a small fix to session handling. The tests pass and the model reviewers find no problem. Should the gate approve it?

Our policy says another engineer must review authentication changes. That requirement survives a favourable model review. The useful report explains why the change needs a person, which checks support it and what that person still needs to decide.

The illustration follows that example through the service. A later commit, a finished test or a new human review can change the evidence, so the decision always belongs to a particular revision.

The worker captures the pull request's state and the policy from its target branch. Model calls return structured findings; they have no GitHub tools. A pure evaluator applies the policy to those findings and the captured evidence, returning a decision without making external calls. A separate GitHub client publishes the result after the service checks that the inputs and permissions are still current and the worker still owns the review. That separation lets us test policy decisions without buying model calls or writing reviews to a repository.

The decision layer is the part we need to own: how repository policy, trusted checks and human approval fit together. Keeping it separate lets us replace a model reviewer while retaining those controls, then measure whether its findings improve the review.

## The team owns the review policy

The implementation calls a routine eligible change **Standard** and a change needing a second engineer **Normal**. These are review routes. A Standard classification is not a certificate that the code is safe, and a high risk grade can reflect a policy restriction rather than a defect the models found.

Protected paths include authentication, permissions, secrets, infrastructure, delivery workflows and migrations. We can require a second engineer for an entire repository too. Emergency changes always need human review. These are choices about where we want human accountability; a model's confidence cannot change them.

Repository policy can adapt the organisation defaults, but the gate uses the policy already on the target branch. A pull request cannot rewrite the rules by which it is being judged. If that policy is invalid, the gate reports the problem and cannot approve or send the change for model review. Changes to the policy deserve review because they change who can approve what.

For a broader view, I analysed a separate sample of 951 pull requests the organisation merged in the thirty days to 8 November. With the protected-path list used for that analysis, 66% would have been Standard and 34% Normal before any model was consulted. Infrastructure, workflows and dependency files accounted for many of the restrictions. That shows the reach of the policy, not the safety of the changes. Whether a dependency bump should always need a second engineer remains a team decision we need to justify.

The policy also has to say what counts as evidence. In the pilot, reviewers spotted a flaw in our required-scanner rule: any workflow could have used the scanner's name. We changed the rule to require a successful result from the expected GitHub App. A familiar label was not enough.

Tests need the same care. A passing security scan does not establish that a test suite ran. Each repository names the test or build checks it relies on for automatic approval; without that policy, a human has to verify the change. Once a check is required, another green check or a human approval cannot excuse its absence or failure.

## More reviewers made escalation too easy

In the first version, the highest risk grade from any reviewer determined the route, and anything above low meant a second engineer. With up to fourteen reviewers, one cautious response could dominate the result. Several repeatedly suggested medium, including on one-line changes. Only two of twelve pilot cases ever reached the Standard route.

Most grades are now advisory. The provisional threshold for requiring another engineer is at least two distinct review lenses grading the change high. Asking the same question through a second provider still counts as one lens. Missing review coverage or substantial provider disagreement can also require a person.

That gives us a more selective rule, but it is still a rule we chose. We need to evaluate its effect on missed defects and reviewer effort before treating it as an improvement in safety.

## Agreement was harder to interpret than a vote count

A 147-line change received 67 findings. An early grouping heuristic reduced them to 27 groups, but grouping by a shared line or similar wording could combine unrelated objections. The implementation now groups matching claims at the same file and line, preserving each report's severity and confidence.

Under the current defaults, a high-severity finding blocks only when two reviewers each report the matching claim at high or critical severity and confidence of at least 0.7. One critical finding at that confidence can block on its own. A serious finding below the blocking threshold still requires a human decision.

The confidence scores gave me reason to question that cutoff. One provider's median was 0.55; the other provider's scores mostly sat between 0.94 and 0.99. On one real pull request, every blocking finding came from the second provider. A shared numeric threshold was treating different scoring habits as if they meant the same thing.

These are self-assessments, not measured probabilities of correctness. Corroboration may reduce noise, but reviewers can share a blind spot. The threshold and quorum need an owner and human-labelled examples against which to judge them. They should not acquire authority simply because they are expressed as numbers in a configuration file.

## Several models could agree and still miss the intent

In one planted case, seven reviewers treated an intentional removal of validation as a silent regression. The description was the only signal of intent. It was reasonable to question the author's claim, but agreement among reviewers did not settle whether the change was correct.

There were useful findings too. Beyond the scanner-identity problem, five review lenses flagged environment-specific deployment settings placed in a shared base, where they would have carried into another environment. Both providers also spotted a planted credential. Those examples justify investigating the tool further. They do not yet establish that the full set of reviewers earns its cost over one good reviewer.

## A size limit was answering the wrong question

The first version skipped model review above 1,500 added plus deleted lines and required a human instead. I picked the number as a cost guard without measuring anything. It counted lockfiles, fixtures and generated code, so a 10,802-line test fixture was treated as a reason to escalate the change.

Across the 951 pull requests in the organisation sample, the median was 144 changed lines and a tenth exceeded 1,500. The ceiling would have affected a meaningful share of work, but those counts told us nothing about whether it selected the changes that needed closer review. [Rootly's argument against small-PR rules](https://rootly.com/blog/why-we-got-rid-of-our-small-pr-rule) helped clarify the mistake: line count was standing in for an assessment of the change.

The line ceiling is gone. Each reviewer now has a **diff-context budget**, provisionally set to 60,000 estimated tokens. That is a capacity limit, not a risk score. If the review cannot cover the whole change, the report names the omissions and requires human review. Generated code and fixtures can still contain consequential changes.

The team owns that budget and the required coverage. A model can point out missing context or suggest where to investigate, but it should not waive a review requirement or raise its own spending allowance. One repository still has a separate four-hundred-line check; while it remains required, the gate respects it. Removing our own arbitrary rule does not justify silently bypassing someone else's policy.

### What the review cost

The original pilot's twelve pull requests, including planted test cases, produced 212 evaluations as checks finished and discussions changed. Only 35 bought a fresh review pass across the applicable model reviewers. Later evaluations could reuse those findings while their inputs remained unchanged, but still reassessed the current checks and approvals. Estimated model spend was about \$14 in total, averaging \$0.41 per fresh pass, with a maximum of \$1.48. A fresh pass took a median of 78 seconds.

That made the original cost rationale for the line ceiling look weak. It did not make cost irrelevant. More reviewers, longer responses and repeated calls can all increase the bill. These historical figures are estimates, not reconciled provider bills.

New decision records retain each reviewer's provider and model, reported token usage and the prices applied to a fresh review. That makes the recorded estimate reproducible without relying on today's price configuration. Reused findings are marked as cached and add no new model spend; missing prices remain explicit. Older records cannot gain missing usage or pricing retroactively, and interrupted requests and retries still need reconciliation against provider bills.

The larger unknown is the full cost: hosting, storage, operations and engineers' time reading or disputing findings. Reading sixty-seven findings on a small change can be expensive even if generating them is cheap. I would measure cost per reviewed PR and per finding an engineer accepts, alongside review time and missed defects. We have not yet measured a net saving.

## What an approval actually means

The code supports two modes. **Shadow** publishes the report and records what the gate would decide, without approving or requesting changes. **Enforce** can issue those reviews when policy permits. The pilot described here included a recommendation-only phase. Shadow is the application default, but the committed deployment manifests explicitly select Enforce. The deployed configuration determines the running mode; the code default alone does not establish it. The examples below illustrate both modes.

A Normal change needs approval from an authorised human other than its author, on the commit being judged. A stale approval does not count, and another person's approval does not cancel an active request for changes. Our production process also requires independent human approval. If merging deploys directly, that approval has to happen before the merge.

The examples use invented pull requests to show waiting for approval, approval by the gate, approval by a human and changes requested. Open **Full report** for the reasoning behind each outcome.

In **Human approved**, the authentication change satisfies its review requirement and the check passes, while the gate continues to withhold its own approval for a Normal change. In **Changes requested**, a human approval cannot erase the blocking finding.

That exposes an unfinished part of enforcement: there is no dedicated way to dismiss or appeal a blocking finding. The model also does not read replies explaining why it is wrong. Before broadening its authority, we need a way for an authorised person to dismiss a specific finding, record the reason and preserve the decision. Asking authors for cosmetic code changes to escape an objection would defeat the point.

Approval also has a lifetime. The gate reassesses when evidence changes and checks it again before acting. In enforce mode it withdraws its previous approval when a new evaluation starts, which can create review churn. A new commit or an outage can still arrive between checking and acting; GitHub's stale-review and required-check protections remain necessary. Switching to shadow does not itself remove approvals issued earlier.

## Be explicit about what leaves the repository

Enrolling a repository is also a data-sharing decision. External model review is enabled by default when providers are configured. A repository can opt out with `externalReview: false` in its target-branch policy and use policy checks with human review instead. Enrolment does not make the data safe to send: the service does not automatically remove credentials, personal data or customer content from the description and diff. Provider terms and what is allowed into source control remain part of that decision.

The same input can contain instructions intended to influence the reviewers. Protected paths limit what a model can overrule, but we have not established that the review process resists prompt injection. Agreement between models is not evidence that hostile input failed to influence them.

## Be able to explain the decision later

When a change causes an incident, the latest green check is not enough. I need to reconstruct what was reviewed, what supported the decision and who had authority to make it. The same history matters when investigating a false positive or explaining a release to an auditor.

Application logs help diagnose the service. When the gate reaches a policy decision, its evidence record includes the head and base commits, the effective policy itself, model identities, reviewer and evaluator version identifiers, check results, human-review evidence and gaps in coverage. Action identifiers connect the attempted writes to the GitHub outcomes observed. Input fingerprints identify the material reviewed; they do not preserve that material or make a model response reproducible.

| Question | Evidence to retain |
| --- | --- |
| What prompted the review? | The event and the revision being assessed. |
| Which rules applied? | The saved policy and reviewer and evaluator version identifiers. |
| What supported the decision? | Test results, human approvals, model findings and gaps in coverage. |
| What actually happened? | The recommendation, action attempted and outcome confirmed by GitHub. |
| Who intervened afterward? | The actor, reason and effect of a retry or intervention. |

“Approval requested” does not prove an approval was created. If GitHub accepts it but the response is lost, the gate has to establish what happened before trying again. Uncertainty must remain visible in the record.

PostgreSQL holds pending work and decision history. Workers coordinate ownership of each pull request and stop initiating actions if they lose it. This makes the database part of the approval path. GitHub remains a separate system: after an uncertain request, recovery inspects current state and evaluates the change again instead of replaying an old approval.

The database enforces the history boundary too. Application credentials can append evidence but cannot update or delete it; database triggers supply the recording time and database identity. Startup rejects administrative or history-editing credentials. Administrators still control the database, and a shared database account cannot establish which individual operator intervened. Access, retention and tested recovery need an accountable owner.

There is another attribution problem specific to AI-assisted work. None of the 951 pull requests in the organisation sample had a bot author, even though the team was using AI. Excluding bot accounts from automatic approval tells us little about how code was written. At our auditor's request, the PR template now records the AI tool, model and what the author reviewed. That information is retained with the evidence. It is optional and self-reported, so it cannot establish provenance on its own.

The dashboard illustrates how the history could be explored. Select an evaluation and open **Delivery and decision trail** to see its evidence. All records, costs and timings here are invented. One PR can produce several evaluations, so evaluation counts must not be presented as the number of changes reviewed.

## What would justify more authority

The next step is to compare CI alone, one reviewer and the full set of reviewers on held-out changes with human-labelled outcomes. We need to count useful findings, false positives and missed defects, then measure how much work each approach creates for engineers. Reducing the number of blocking reports is not enough if it also hides defects.

Model, prompt and policy changes should be judged against that evidence. Enforcement also needs the appeal process described above and demonstrated recovery from outages, including cases where GitHub and the gate temporarily disagree about what happened. Passing local tests cannot prove that production recovery works.

Before expanding enforcement, I would name who owns stalled reviews, who can authorise an exception and who is accountable for the decision record. Those are rollout requirements alongside evidence that the extra review finds useful defects without creating more investigation work than it saves.

For now, the strongest case for the gate is the preparation it gives a reviewer: relevant evidence, specific objections and a record of the decision. Giving it more authority should depend on whether that preparation measurably improves review, and whether we can account for its failures.
